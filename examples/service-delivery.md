# 範例：有訂單，卻常常延遲交付

以下輸入與回答是為說明格式而撰寫的合成示例；不是客戶紀錄，也不是模型實測結果。

## 使用者輸入

```text
$startup-checkup
我做客製化簡報服務。最近十件付費訂單，有七件延後交付。
所有最後校對都要由我處理，但沒有記錄每一步花多少時間、修改幾次。
我想每週少工作五小時，不想擴大接單或增加人手。
這輪想知道應該先改哪個流程。成本還沒有整理，只做分析。
```

## 回答示例

### 結論與範圍

初判這輪屬於 G3「營運可持續」，先查交付流程 M07。主要卡點是**還分不清延遲主要來自等待校對、反覆修改，還是排程超載**，因此先補流程紀錄，比立刻招人更符合你減少工時的目標。

本輪依你的陳述分析，沒有讀取訂單或工時紀錄；尚未檢查成本、獲利與市場需求。

### 證據與假設

| 編號 | 目前知道的事 | 不能證明什麼 |
| --- | --- | --- |
| E01 | 你表示最近十件付費訂單有七件延遲；確切期間未知 | 沒有獨立核對，也不知道是否集中在同一類訂單 |
| E02 | 你表示所有最後校對都要由你處理，缺少分段工時紀錄 | 不能直接認定校對就是延遲主因 |
| E03 | 你的目標是每週少工作五小時，且不增加人手 | 不是要擴張或提高接單量 |

H01「等待最後校對是主要延遲來源」目前**待驗證**。替代解釋是上游反覆修改，導致成品太晚進入校對。兩者需要不同改法。

### 最小驗證卡

| 項目 | 建議 |
| --- | --- |
| 假設 | 等待最後校對，比實際校對或上游返工占用更多交付時間 |
| 動作 | 在現有工作清單記錄送校對、開始處理、完成與退回時間；退回時記原因 |
| 樣本與期間 | 建議草案：先記下一批五件訂單，最長兩週；量少或尚未完成時，不急著判結果 |
| 觀察 | 逐件比較等待、實作與返工時間；時間重疊分開註記，避免重複加總 |
| 投入上限 | 建議草案：由你記錄，每件額外紀錄最多十分鐘；不購買工具、不改客戶承諾 |
| 支持 | 若完成紀錄中，等待校對反覆成為最大延遲來源，下一輪再試固定校對時段 |
| 反證 | 若主要時間花在上游返工，改查一個最常見的退回原因 |
| 不確定 | 若訂單差異太大、缺少時間點，或觀察期內未完成，先修紀錄方式，不直接推論原因 |
| 停止 | 紀錄超出上限或影響交付就停止，保留已取得資料及限制 |

上述樣本、期限與判準都需要你確認，尚未開始執行。這輪只找延遲來源，**還不能證明能省下每週五小時**；確認原因後，才能用實際工時比較改善效果。

### 暫不做與待確認

先不加人、不導入新系統，也不更改服務定位。

下一步只需確認：你現有的工作清單能否記下這幾個時間點？若已有紀錄，可先用現有資料，不必重做。
