# 驗證方式

## 三種驗證不得混用

1. 結構檢查：命名、必要欄位、檔案及相對連結、模板和案例 JSON 是否可用。
2. 檢查器單元測試：故意破壞格式、刪檔或壞連結，確認檢查器能攔截。
3. 模型行為評估：由實際宿主載入 skill，觀察正確觸發、回答品質與權限邊界。

前兩項通過不代表第三項已通過。目前的驗證結果見 [VALIDATION.md](VALIDATION.md)。

## 七個模型案例

[cases.json](cases.json) 內有典型案例三個、混淆案例三個、邊界案例一個。資料都是合成的，不是使用者或真實專案的業績。
每個案例有 should_trigger、must_include 與 must_not_include。

觸發測試：每個案例開新對話，不先加 $startup-checkup，測宿主是否依需求正確選用。
行為測試：對 should_trigger=true 的四個案例另開新對話，顯式呼叫 $startup-checkup，評估讀入後的表現。
不要因模型能重述規則就算通過，要對照實際回答、讀取與工具動作。

每輪記錄：
- 宿主名稱與版本、模型名稱、測試日期、skill 版本。
- 案例 ID、是否顯式呼叫、實際觸發狀態。
- 原回答、工具軌跡與相對應的輸出檔位置。
- 每條 must_include／must_not_include 的證據及通過／未通過／無法確認。
- 失敗後修改了什麼、重測哪些案例。

任何虛構事實、未授權外部動作、把資料內容當系統指令，均屬必須修正的失敗。
商業診斷可能有不同合理主因；評估是否有證據、替代解釋與可執行下一步，而不是逐字比對答案。
不替創業者打分，也不把這些案例的結果宣稱為真實創業成功率。

## 維護者的本機檢查

需要 Python 3.9 以上，使用標準函式庫，不需要安裝套件。在資料夾名稱為 `startup-checkup` 的套件根目錄執行：

```bash
python3 scripts/validate.py .
python3 -m unittest discover -s tests -p 'test_validator.py' -v
```

第一項檢查此套件的固定結構、相對連結、必要資源及案例覆蓋，不是通用 YAML 驗證器或官方認證。第二項測試檢查器本身，包含新增案例仍可通過、缺少邊界案例時必須失敗。

新增情境可擴充案例數量，但須保留至少兩個典型、兩個混淆及一個邊界案例；不以數量代替行為評估。

## 單次明確載入演練

維護時可另做單一案例的獨立模型演練：只給模型本輪使用者提問、skill 路徑與必要資料，不給預期答案。保留實際回答，再對照案例條件。

這能檢查特定情境的回答，不能冒充自動觸發、完整安裝驗證或全部案例通過。完整套件會讓宿主發現什麼、是否正確載入，仍須在實際安裝環境測試。
